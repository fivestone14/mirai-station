## 1. Verdict

The core of the build holds up. The grader and the labels share one morning anchor. No ranking base includes today. The plist times, weekday gates and holiday calendar are right. All 30 of Monday's graded results re-grade exactly. Every label and constant the question set names exists in the code. The trouble is in the data paths, and the first live day showed it. The context job keeps only one breadth minute per run, so about one minute in six was never saved and some opening TICK answers changed. Other symbols were priced from quotes up to 70 seconds old and compared against SPX bar closes. Tape reads can reuse an old diary row and still call it fresh. On grading: close-outs get a single attempt, which is why Monday's pre-market 30-minute call is still ungraded. The learning loop's frozen baseline was counted with the old ruler. A call that can never be graded is still counted as "still to grade". The phone has one path that breaks the page (a diary row with no wall) and a few states that show nothing and give no reason. The docs and the question set's own counts lag the code. After merging duplicates found by more than one lens: **56 confirmed findings (13 bugs, 30 inconsistencies, 13 cleanups), 11 disputed, 4 rejected.**

## 2. Confirmed findings (both skeptics agreed)

### Bugs (13)

**B1. The context job saves one breadth minute per run, so today's TICK counts run on gaps.** *Where:* `spx_jev/market_context.py:79-85` (`line["bars"][symbol] = done[-1]`), plist StartInterval 60; read by `labels/breadth.py:210-219, 529-590`. *What:* each run fetches every $TICK/$TRIN/$UVOL/$DVOL minute since the open but keeps only the newest. launchd waits 60 s after each run ends, so runs land about 70 s apart. 68 of 390 minutes were missing on 09-28: 55 from that drift, and 13 from the 09:57-10:09 OAuth outage, which the next good run fetched again and threw away. The prior sessions it ranks against are complete backfill. *Impact:* replays show `opening_tick` said "twice, short of the 3-burst count" at 10:15-10:30 when complete data has 3 bursts (the lost 10:10 bar), with a 10:30 mean of +19 vs +38. `tick_side_vs_usual` and `volume_vs_count_30m` were dropped with "have 17" when complete data has 30. `opening_tick_lean` was answered two_way_open, where its own rule gives one_sided_buying. A burst in a lost minute makes `tick_extreme_follow` sleep, so missing data is treated as "nothing happened" (seen in replay at 13:22, not in a live read). $VIX1D has no history, so its lost minutes are gone for good. *Fix:* append every finished bar not yet on disk, as `bars.py:53` already does. Have the breadth labels skip with a reason when a window has gaps. Consider StartCalendarInterval so runs line up with the minute. (Found by the point-in-time, jobs and data-stores lenses.)

**B3. (Also found by the robustness lens.)

**B4. shock_fingerprint offers a one_name option that nothing can make true.** *Where:* `labels/events_shocks.py:809`; option at `spec/question_set.json:7033`; `ONE_NAME_SHARE` (`cuts.py:155`) is used by no calculation. *What:* the label always says in fixed words that no megacap share is measured, and never reads the weights. *Impact:* JEV was offered the option at 13:30 and 14:01 (it answered rates_led).
